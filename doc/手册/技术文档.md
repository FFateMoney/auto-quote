# 自动报价系统技术文档

本文档面向系统接手开发人员，说明自动报价系统的当前功能模块、运行链路、数据接口、数据库模型、部署配置和排障入口。当前运行实现以 `backendV2/` 和 `frontendV2/` 为准：Agent 负责阅读文件、识别独立试验需求并填写报价表；Core 负责设备匹配、计价、运行记录、导出和目录管理。

旧版 `backend/` 中的 OCR、清洗、索引和 Qdrant 链路不参与当前报价流程，也不应作为当前服务启动或维护的入口。标准库现以已准备好的 Markdown 与原始 PDF 文件供 Agent 按需查阅。

## 当前架构

```text
浏览器
  │
  ▼
frontendV2 (React + Vite, :3000)
  │  /api 反向代理
  ▼
backendV2 Core (FastAPI, :7887)
  ├── PostgreSQL
  │     ├── 测试项目、价格、适配设备与设备能力
  │     ├── 专有字段比较协议
  │     └── 历史报价与可复用标准条件
  ├── agent_workspace/runtime/<run_id>/
  │     ├── 输入文件、Agent 报价表、提交结果、计算结果、人工快照
  │     └── Agent 执行日志
  └── 项目内固定 Codex CLI
          └── DashScope qwen3.7-plus
```

| 组件 | 职责 |
|---|---|
| `frontendV2` | 文件与文本提交、结果展示和修改、设备选择、导出、历史报价保存、数据库目录管理。 |
| `backendV2/core/runs` | 创建运行目录、后台启动 Agent、读取提交结果、保存状态与报价快照。 |
| `backendV2/core/tools` | Agent 可调用的命令行接口，负责目录查询、动态表单生成、历史缓存读取、格式校验和批量提交。 |
| `backendV2/core/quoting` | 根据测试项目、设备能力和比较规则筛选设备，计算价格。 |
| `backendV2/core/catalog` | 测试项目、设备能力、别名和专有字段定义的数据库访问与管理。 |
| `backendV2/core/history` | 保存用户确认后的报价，并按标准类型、测试项目、标准号提供可复用的标准条件缓存。 |
| `backendV2/core/exports` | 使用 Word 模板生成报价单，并保存导出快照。 |
| `backendV2/agent_workspace` | Agent 的提示词、专用 Codex 配置和每次报价的独立工作目录。 |

## 报价流程

### 创建运行

前端调用 `POST /api/runs`。第一个文件为报价需求文件，其余文件为参考资料；粘贴文本时，前端先生成 UTF-8 文本文件，再按相同方式提交。

Core 创建 `run_id`，将全部输入保存到：

```text
backendV2/agent_workspace/runtime/<run_id>/input/
```

同时生成通用 JSON 外层 Schema，并在 `backendV2/core/runtime/<run_id>/state.json` 记录运行状态。

### Agent 提取与提交

Core 在后台以项目内固定版本的 Codex CLI 启动报价 Agent。Agent 的工作目录固定为 `backendV2/agent_workspace/`，入口提示词是 [extract_quote.md](/my_storage/chen/auto-quote/backendV2/agent_workspace/prompts/extract_quote.md)。

Agent 的工作步骤如下：

1. 阅读本次 `input/` 中的报价需求与参考文件。
2. 将需求拆分为原子报价：一个独立试验需求对应一张报价表；试验条件、标准章节、样品数量或计价数量不同的需求不合并。
3. 调用 `quote-core query-test-projects` 获取测试项目三元组：`标准类型 + 测试项目 + 最大规格`。
4. 选择对应的 `test_project_id`。无法精确匹配时，才调用别名查询工具作为参考；确实无法匹配时保留 `test_project_id: null`，但仍单独建表。
5. 对已匹配项目调用 `quote-core query-test-project-capability-fields`，取得该项目的动态报价表模板。
6. 按模板填写固定字段和专有字段。来源没有明确值时填写 JSON `null`。
7. 将每份报价写入 `quotes/<quote_id>/quote_table.json`，逐份执行格式校验。
8. 调用一次 `quote-core submit-batch` 提交本次运行的全部报价表。

报价表的统一外层格式：

```json
{
  "schema_version": 1,
  "test_project_id": 12,
  "values": {
    "固定字段": {
      "raw_test_type": "振动试验",
      "standard_code": "MIL-STD-810G",
      "standard_document_section": "514.6C-I",
      "pricing_mode": "时长",
      "specification": "振动台",
      "pricing_quantity": 15,
      "sample_count": 1,
      "length_mm": 300,
      "width_mm": 250,
      "height_mm": 50
    },
    "专有字段": {
      "frequency_min_hz": 10,
      "frequency_max_hz": 2000
    }
  }
}
```

固定字段名称定义在 [templates.py](/my_storage/chen/auto-quote/backendV2/core/submissions/templates.py)。专有字段由测试项目适配设备的非空能力字段动态生成，字段集合保存在 `test_project_capability_sets`。

### 知识补全

Agent 在需要依据标准补全试验条件、时长、循环或性能参数时，按以下优先级读取资料：

1. 报价需求文件本身；
2. 本次 `input/` 内的参考资料；
3. 已保存的历史报价标准条件缓存；
4. `data/cleaned_markdown/` 内的标准文本；
5. `data/origin/` 内对应的原始 PDF。

标准编号必须实质一致。对于 PDF，文字层用于定位章节；曲线图、扫描页、图片表格等内容由 Agent 渲染页面后以视觉能力读取。样品尺寸只允许来自报价需求文件及其输入附件，不从标准库推断。

### Core 设备筛选与计价

`submit-batch` 先校验每张 JSON 报价表的外层格式，校验通过后由 `CoreQuotationService` 处理：

1. 通过 `test_project_id` 取得价格、适配设备集合、标准类型、测试项目、最大规格和计价方式。
2. 读取该项目所有未删除的适配设备。
3. 对报价表的每个非空专有字段，读取 `special_field_definitions` 中定义的比较方式，并判断设备能力是否满足需求。
4. 任一侧能力值为空时跳过该字段比较；双方都有值时按比较协议判断。
5. 将可用设备按功耗从低到高排序，默认选择功耗最低的设备。
6. 按公式计算金额：

```text
总价 = 基本金 + 单价 × 计价数量
```

设备可选性与金额计算是两个独立结果。已选择测试项目且计价数量存在时，系统可以计算价格；可选设备列表为空时，前端仍可展示并允许用户修改信息后重新筛选。

比较逻辑集中于 [matching.py](/my_storage/chen/auto-quote/backendV2/core/quoting/matching.py)：

| 比较类型 ID | 比较语义 |
|---|---|
| `0` | 设备值小于等于需求值，例如设备最低温度。 |
| `1` | 设备值大于等于需求值，例如设备最高温度、最大负荷。 |
| `2` | 设备值等于需求值。 |
| `3` | 需求值包含于设备能力集合。 |

## 运行目录与快照

每个报价运行均为独立文件边界：

```text
backendV2/agent_workspace/runtime/<run_id>/
├── input/                              # 原始需求与参考文件
├── quote_table.schema.json             # 通用提交外层 Schema
├── test_projects.json                  # Agent 查询得到的项目目录
├── aliases/                            # 按需查询的别名结果
├── schemas/                            # 按项目生成的动态报价模板
├── history_cache/                      # 按需查询的历史报价标准条件
├── quotes/
│   └── <quote_id>/
│       ├── quote_table.json            # Agent 提交的独立报价表
│       ├── validation_result.json      # 单表格式校验结果
│       └── snapshots/                  # 前端人工修改快照
├── submit_result.json                  # 批量提交结果
├── quotation_results.json              # Core 的初始筛选和报价结果
├── quotation_results_output.json       # 最近一次导出使用的报价快照
├── 报价单_<run_id>.docx                 # 导出的 Word 报价单
└── agent_execution.jsonl               # Codex Agent 执行日志
```

Core 运行状态位于 `backendV2/core/runtime/<run_id>/state.json`：

| 状态 | 含义 |
|---|---|
| `created` | 文件已保存，尚未启动 Agent。 |
| `agent_running` | Agent 正在分析文件。 |
| `submitted` | Agent 已提交且 Core 接受报价表。 |
| `submission_rejected` | Agent 正常退出，但报价表未通过格式校验。 |
| `agent_failed` | Agent 进程异常退出。 |

前端人工修改报价、切换项目规格、选择设备或切换“基本金归 0”时，Core 不覆盖 Agent 原始表，而是在对应 `quotes/<quote_id>/snapshots/` 下创建新的报价快照。结果查询、导出和保存历史报价优先使用最新人工快照。

## 数据库模型

数据库连接从 `backend/dev/config.yaml` 的 `database` 段读取。核心表如下：

| 表 | 用途 |
|---|---|
| `test_projects` | 报价项目主表。每行是一个 `标准类型 + 测试项目 + 最大规格` 三元组，包含计价方式、基本金、单价、适配设备集合、别名和软删除状态。标准类型不是独立表，而是此表的分组字段。 |
| `device_capabilities` | 每个设备一行，包含尺寸、温湿度、水路、辐照、振动、载荷、功耗等能力和软删除状态。 |
| `test_project_capability_sets` | 每个测试项目一行，记录该项目适配设备非空能力字段的并集；它决定 Agent 动态表单的专有字段。 |
| `special_field_definitions` | 专有字段名及比较类型 ID，是设备筛选协议的唯一字段定义来源。 |
| `historical_quotations` | 用户从前端保存的历史报价，每个报价项一行，包含来源运行、快照、字段、价格和选中设备。 |
| `historical_quotation_reuse_fields` | 标记哪些历史字段可按标准条件复用，并定义缓存分组范围。 |

目录管理 API 支持测试项目与设备的新增、编辑、软删除、恢复；测试项目别名可独立维护。编辑设备或项目适配设备集合时，系统会同步刷新对应的动态能力字段集合。

### 初始化目录数据库

初始目录来自 `doc/新试验类型及设备能力.xlsx`。以下命令会重建测试项目、设备能力与动态字段集合，并初始化专有字段定义和历史报价表：

```bash
cd /my_storage/chen/auto-quote
/my_storage/chen/conda/envs/quote/bin/python -m backendV2.core.catalog.bootstrap_database
```

该命令执行 `001_replace_catalog.sql`，会替换现有目录表数据，只应在初始化或明确需要重建目录时执行。日常目录维护应通过前端数据库管理页或对应 API 完成。

## HTTP API

所有接口由 Core 提供，前端通过 `/api` 代理访问。

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/health` | `GET` | Core 健康检查。 |
| `/api/runs` | `GET` | 列出运行记录。 |
| `/api/runs` | `POST` | 上传报价需求文件和参考文件，创建并后台运行报价任务。 |
| `/api/runs/{run_id}` | `GET` | 查询运行状态。 |
| `/api/runs/{run_id}/source-file` | `GET` | 下载原始报价需求文件。 |
| `/api/runs/{run_id}/quotation-results` | `GET` | 获取报价表、价格、可选设备和规格选项。 |
| `/api/runs/{run_id}/quotations/{quote_id}/recalculate` | `POST` | 依据前端修改后的字段重新筛选设备并保存报价快照。 |
| `/api/runs/{run_id}/quotations/{quote_id}/snapshot` | `POST` | 保存当前报价快照。 |
| `/api/runs/{run_id}/quotations/base-fee-override` | `POST` | 批量开启或关闭本次运行的基本金归零。 |

| `/api/catalog/test-projects` | `GET/POST` | 查询或新增测试项目。 |
| `/api/catalog/test-projects/{id}` | `PUT/DELETE` | 编辑或软删除测试项目。 |
| `/api/catalog/test-projects/{id}/restore` | `POST` | 恢复测试项目。 |
| `/api/catalog/test-projects/{id}/aliases` | `PUT` | 更新测试项目别名。 |
| `/api/catalog/devices` | `GET/POST` | 查询或新增设备能力。 |
| `/api/catalog/devices/{id}` | `PUT/DELETE` | 编辑或软删除设备。 |
| `/api/catalog/devices/{id}/restore` | `POST` | 恢复设备。 |

### 运行接口数据结构

#### 创建运行

`POST /api/runs` 使用 `multipart/form-data`，字段名为 `files`，可重复传入。文件顺序具有业务含义：

```text
files[0]  = 报价需求文件
files[1:] = 参考文件
```

创建成功返回 HTTP `202`：

```json
{
  "run_id": "Vibration_Test振动测试_20260908153000",
  "status": "created",
  "uploaded_file": "Vibration_Test振动测试.xlsx",
  "created_at": "2026-09-08T07:30:00+00:00",
  "updated_at": "2026-09-08T07:30:00+00:00",
  "agent_return_code": null
}
```

前端随后轮询 `GET /api/runs/{run_id}`。当 `status` 变为 `submitted` 时，再读取报价结果。

#### 报价结果

`GET /api/runs/{run_id}/quotation-results` 返回：

```json
{

    {
      "quote_id": "quote-001",
      "test_project_id": 12,
      "fixed_fields": {
        "raw_test_type": "Vibration Testing",

        "test_item": "随机振动",
        "standard_code": "MIL-STD-810G",
        "standard_document_section": "514.6C-I",
        "pricing_mode": "时长",
        "specification": "振动台",
        "pricing_quantity": 15,
        "sample_count": 1,
        "length_mm": 300,
        "width_mm": 250,
        "height_mm": 50
      },
      "special_fields": {
        "frequency_min_hz": 10,
        "frequency_max_hz": 2000
      },
      "base_fee": 500,
      "unit_price": 50,
      "pricing_mode": "时长",
      "pricing_quantity": 15,
      "total_price": 1250,
      "selected_device_code": "D16",
      "eligible_devices": [
        {
          "device_code": "D16",

          "test_project_id": 12,
          "specification": "振动台",

```

`fixed_fields` 和 `special_fields` 是前端显示与人工修改的业务数据。`eligible_devices` 已按功耗排序，`specification_options` 用于规格下拉选择。

#### 保存修改与重新报价

以下两个接口使用相同请求体：

- `POST /api/runs/{run_id}/quotations/{quote_id}/recalculate`
- `POST /api/runs/{run_id}/quotations/{quote_id}/snapshot`

```json
{
  "test_project_id": 12,
  "fixed_fields": {
    "raw_test_type": "Vibration Testing",
    "standard_type": "振动",
    "test_item": "随机振动",
    "standard_code": "MIL-STD-810G",
    "pricing_mode": "时长",
    "specification": "振动台",
    "pricing_quantity": 18
  },
  "special_fields": {
    "frequency_min_hz": 10,
    "frequency_max_hz": 2000
  },
  "selected_device_code": "D16",
  "base_fee_override": null
}
```

响应为更新后的单个报价结果对象。Core 会重新读取项目价格、筛选设备、计算总价，并写入新的人工快照。

#### 批量基本金调整

`POST /api/runs/{run_id}/quotations/base-fee-override`：

```json
{"enabled": true}
```

`true` 将本次运行全部报价的基本金覆盖为 `0`；`false` 删除覆盖值并恢复项目本金。响应结构与报价结果接口一致。

#### 历史保存和导出

`POST /api/runs/{run_id}/history-quotations` 不需要请求体，返回：

```json
{"saved_count": 3}
```

`POST /api/runs/{run_id}/export` 默认导出全部总价非空的报价；传入查询参数 `quote_id` 时只导出指定报价：

```text
/api/runs/<run_id>/export?quote_id=quote-001
```

响应为 Word 文件流，媒体类型为 `application/vnd.openxmlformats-officedocument.wordprocessingml.document`。

### 目录管理接口数据结构

测试项目新增和修改使用相同结构：

```json
{
  "standard_type": "高低温",
  "test_item": "高低温",
  "max_specification": "2.4",
  "pricing_mode": "时长",
  "base_fee": 500,
  "unit_price": 50,
  "applicable_device_codes": ["D16", "D17"]
}
```

别名更新接口请求：

```json
{
  "aliases": ["高温试验", "低温试验", "Temperature Test"]
}
```

设备新增和修改请求：

```json
{
  "device_code": "D16",
  "capabilities": {
    "max_volume_m3": 2.4,
    "temperature_min_c": -70,
    "temperature_max_c": 180,
    "max_load_kg": 500,
    "power_kwh": 12.5
  }
}
```

测试项目与设备的删除接口返回 HTTP `204`，只修改软删除状态；恢复接口返回：

```json
{"restored": true}
```

### 错误响应

HTTP API 使用 FastAPI 标准错误格式：

```json
{"detail": "run_not_found"}
```

常见状态码：

| 状态码 | 含义 |
|---|---|
| `400` | 请求字段或业务输入无效。 |
| `404` | 运行、报价、项目、设备或源文件不存在。 |
| `500` | 导出或服务内部处理失败。 |

## Agent 命令工具

Core 通过 `backendV2/core/tools/bin/quote-core` 向 Agent 提供命令。所有文件参数必须位于本次运行目录内。

| 命令 | 生成或执行内容 |
|---|---|
| `quote-core query-test-projects --run-dir <run_dir>` | 生成 `test_projects.json`。 |
| `quote-core query-test-project-aliases --run-dir <run_dir> --test-project-id <id>` | 生成项目别名文件。 |
| `quote-core query-test-project-capability-fields --run-dir <run_dir> --test-project-id <id>` | 生成对应项目的动态报价字段模板。 |
| `quote-core query-history-quotation-cache --run-dir <run_dir> --standard-type <x> --test-item <y> --standard-code <z>` | 生成可复用历史标准条件缓存。 |
| `quote-core validate-quote-table --run-dir <run_dir> --file quotes/<quote_id>/quote_table.json` | 校验单份报价表 JSON 格式。 |
| `quote-core submit-batch --run-dir <run_dir>` | 校验并提交运行目录中全部报价表，同时产生初始报价结果。 |

Agent 与 Core 不以标准输入输出直接传输报价 JSON；报价数据始终先写入本次运行目录，工具只传递文件或目录路径。这使 Agent 输出、校验结果、人工修改和导出都可以回溯。

## 本地启动

### 前置依赖

- Python 3.11+，当前部署使用 Conda 环境 `quote`；
- Node.js 20+；
- PostgreSQL；

### 配置

Core 默认读取 `backend/dev/config.yaml` 的 `qwen.api_key` 和 `database`。生产或共享环境优先使用环境变量注入 `QWEN_API_KEY`，避免将密钥写入配置文件。

报价 Agent 的模型配置独立于系统用户的 Codex 配置，位于：

```text
backendV2/agent_workspace/codex_home/quote-agent.config.toml
```

当前固定 Agent CLI 版本由 `backendV2/agent_runtime/codex/package-lock.json` 锁定，默认模型为 `qwen3.7-plus`。Core 启动 Agent 时设置专用 `CODEX_HOME`，不读取 `~/.codex`。

| 变量 | 默认值 | 用途 |
|---|---|---|
| `AUTO_QUOTE_CONFIG_PATH` | `backend/dev/config.yaml` | 指定 Core 配置文件。 |
| `QWEN_API_KEY` | 配置中的 `qwen.api_key` | DashScope API 密钥。 |
| `QUOTE_V2_CORE_RUNTIME` | `backendV2/core/runtime` | Core 状态目录。 |
| `QUOTE_V2_AGENT_WORKSPACE` | `backendV2/agent_workspace` | Agent 工作区。 |
| `QUOTE_V2_AGENT_EXECUTABLE` | 项目内 `codex` | 替换 Agent CLI 可执行文件。 |
| `QUOTE_V2_AGENT_PROFILE` | `quote-agent` | Agent 配置 profile。 |
| `QUOTE_V2_CODEX_HOME` | `agent_workspace/codex_home` | Agent 专用 Codex 配置目录。 |
| `VITE_API_PROXY_TARGET` | `http://127.0.0.1:7887` | 前端开发服务器的 API 代理目标。 |

### 启动命令

启动 Core：

```bash
cd /my_storage/chen/auto-quote
QWEN_API_KEY='...' /my_storage/chen/conda/envs/quote/bin/python \
  -m uvicorn backendV2.core.app:app --host 127.0.0.1 --port 7887
```

启动前端：

```bash
cd /my_storage/chen/auto-quote/frontendV2

```

前端监听 `0.0.0.0:3000`，通过 Vite 将 `/api` 转发至 `127.0.0.1:7887`。健康检查：

```bash
curl http://127.0.0.1:7887/api/health
curl http://127.0.0.1:3000/api/health
```

## 前端功能

前端入口在 [App.tsx](/my_storage/chen/auto-quote/frontendV2/src/App.tsx)，主要组件如下：

| 组件 | 功能 |
|---|---|
| `UploadSection.tsx` | 上传一个报价需求文件、多个参考文件，支持拖拽；支持粘贴文本和生成样品信息文本附件。 |
| `StructuredReportGrid.tsx` | 独立报价切换、固定字段与专有字段显示和编辑、测试项目/规格/计价方式选择、设备选择与重新计价。 |
| `EquipmentTables.tsx` | 展示当前报价的可选设备及能力。 |
| `DatabaseManager.tsx` | 按标准类型分组管理测试项目、设备能力、软删除回收站和别名。 |
| `quotationFieldLabels.ts` | 前端字段名中英文显示映射；后端数据字段保持英文。 |

报价页面支持下载源文件、导出全部报价、导出当前报价、保存至历史报价库，以及“基本金归 0”切换。导出时会将当前报价中已匹配项目的 `raw_test_type` 补充为对应测试项目别名，便于后续 Agent 匹配。

## 测试与排障

后端测试：

```bash
cd /my_storage/chen/auto-quote
/my_storage/chen/conda/envs/quote/bin/python -m unittest discover -s backendV2/tests -p 'test_*.py'
```

前端静态检查与构建：

```bash
cd /my_storage/chen/auto-quote/frontendV2
npm run lint
npm run build
```

| 现象 | 首先检查 |
|---|---|
| 运行停在处理中或失败 | `backendV2/core/runtime/<run_id>/state.json` 与 `agent_execution.jsonl`。 |
| Agent 提交被拒绝 | `submit_result.json`、各报价目录的 `validation_result.json`。 |
| 无报价结果 | `quotation_results.json`、`quotes/*/quote_table.json`、运行状态是否为 `submitted`。 |
| 设备为空或总价不符合预期 | `test_project_id`、项目适配设备集合、`special_field_definitions` 和报价表的 `专有字段`。 |
| 前端请求失败 | `curl http://127.0.0.1:7887/api/health`，再检查 `VITE_API_PROXY_TARGET`。 |
| Agent 无法启动或模型调用失败 | 项目内 `codex`、`quote-agent.config.toml`、`QWEN_API_KEY` 和 `agent_execution.jsonl`。 |
