# 自动报价系统维护手册

## 1. 维护范围

当前生产链路由以下部分组成：

- `frontendV2`：React 前端，默认端口 `3000`；
- `backendV2`：FastAPI Core，默认端口 `7887`；
- PostgreSQL：测试项目、设备能力、比较协议和历史报价；
- 项目内 Codex CLI：启动文档分析 Agent；
- DashScope `qwen3.7-plus`：Agent 使用的模型；
- `data/cleaned_markdown` 与 `data/origin`：Agent 按需查阅的标准文本和原始 PDF；
- `backendV2/agent_workspace/runtime`：报价运行工作目录；
- `backendV2/core/runtime`：运行状态目录。

旧版 OCR、清洗、向量索引和 Qdrant 服务不参与当前报价运行。维护当前系统时不需要启动这些服务。

## 2. 运行环境

| 依赖 | 当前约定 |
|---|---|
| 操作系统 | Linux |
| Python | 3.11+，部署环境为 `/my_storage/chen/conda/envs/quote` |
| Node.js | 20+ |
| 数据库 | PostgreSQL |
| 前端 | React 19、TypeScript、Vite 6 |
| 后端 | FastAPI、Pydantic、Psycopg |
| Agent CLI | `@openai/codex`，由项目锁文件固定版本 |
| 模型服务 | DashScope OpenAI-compatible API，`qwen3.7-plus` |

关键文件：

| 文件 | 用途 |
|---|---|
| `backend/dev/config.yaml` | 数据库和 API 密钥默认配置来源。 |
| `backendV2/agent_workspace/codex_home/quote-agent.config.toml` | 报价 Agent 模型和服务地址。 |
| `backendV2/agent_workspace/codex_home/model-catalog.local.json` | Agent 模型能力目录。 |
| `backendV2/agent_workspace/prompts/extract_quote.md` | 报价提取与知识补全规则。 |
| `backendV2/agent_runtime/codex/package-lock.json` | 固定 Codex CLI 依赖版本。 |
| `doc/quote_tep.docx` | Word 报价单模板。 |

API 密钥优先通过 `QWEN_API_KEY` 环境变量注入。共享环境中不应依赖个人目录下的 Codex 配置，报价 Agent 已使用独立 `CODEX_HOME`。

## 3. 服务启动和停止

### 3.1 前置检查

```bash
cd /my_storage/chen/auto-quote
test -x backendV2/agent_runtime/codex/node_modules/.bin/codex
/my_storage/chen/conda/envs/quote/bin/python --version
node --version
```

若项目内 Codex CLI 尚未安装：

```bash
cd /my_storage/chen/auto-quote/backendV2/agent_runtime/codex
npm ci
```

### 3.2 使用 screen 启动 Core

```bash
screen -L -Logfile /tmp/quote-v2.log -dmS quote-v2 bash -lc \
  'cd /my_storage/chen/auto-quote && exec /my_storage/chen/conda/envs/quote/bin/python -m uvicorn backendV2.core.app:app --host 127.0.0.1 --port 7887'
```

### 3.3 使用 screen 启动前端

```bash
screen -L -Logfile /tmp/front-vite.log -dmS front bash -lc \
  'cd /my_storage/chen/auto-quote/frontendV2 && exec npm run dev'
```

当前 `npm run dev` 监听 `0.0.0.0:3000`，并将 `/api` 请求代理到 `127.0.0.1:7887`。

### 3.4 停止和重启

```bash
screen -S front -X quit
screen -S quote-v2 -X quit
```

修改 Python Core、Agent Runner、Core 配置或提示词加载逻辑后，应重启 `quote-v2`。普通前端源码修改由 Vite 热更新；升级依赖或修改 Vite 配置后应重启 `front`。

### 3.5 运行确认

```bash
screen -ls
ss -ltnp | rg ':3000|:7887'
curl --fail --max-time 5 http://127.0.0.1:7887/api/health
curl --fail --max-time 5 http://127.0.0.1:3000/api/health
```

两个健康检查均应返回：

```json
{"status":"ok"}
```

## 4. 配置维护

Core 通过 `backendV2/core/settings.py` 读取配置。主要环境变量如下：

| 环境变量 | 用途 |
|---|---|
| `AUTO_QUOTE_CONFIG_PATH` | 指定配置文件。 |
| `QWEN_API_KEY` | DashScope API 密钥。 |
| `QUOTE_V2_CORE_RUNTIME` | Core 状态目录。 |
| `QUOTE_V2_AGENT_WORKSPACE` | Agent 工作区。 |
| `QUOTE_V2_AGENT_EXECUTABLE` | Agent CLI 可执行文件。 |
| `QUOTE_V2_AGENT_PROFILE` | Agent profile，默认为 `quote-agent`。 |
| `QUOTE_V2_CODEX_HOME` | Agent 专用 Codex 配置目录。 |
| `VITE_API_PROXY_TARGET` | 前端 `/api` 代理目标。 |

修改模型时需要同时核对专用 profile 和本地模型目录中的模型名称及能力声明。修改 Codex CLI 版本时，更新 npm 依赖和锁文件，执行 `npm ci`，完成实际模型连通测试后再重启 Core。

## 5. 数据库维护

### 5.1 日常维护

测试项目、设备能力、适配设备、价格和别名优先通过前端数据库管理页维护。测试项目和设备删除均为软删除，可从回收站恢复。

目录修改关系：

- 修改测试项目适配设备集合，会重建该项目的动态专有字段集合；
- 修改设备能力，会刷新引用该设备的项目能力集合；
- 修改设备编号，会同步更新测试项目中的设备编号引用；
- 导出报价时，当前原始试验类型会补充到匹配项目的别名列表；
- 保存至历史报价库时，同一运行和报价 ID 的记录会更新为最新快照。

### 5.2 数据库表

| 表 | 维护重点 |
|---|---|
| `test_projects` | 标准类型、测试项目、最大规格、计价方式、价格、适配设备、别名、软删除状态。 |
| `device_capabilities` | 设备能力、功耗和软删除状态。 |
| `test_project_capability_sets` | 动态专有字段集合，应由目录维护逻辑自动刷新。 |
| `special_field_definitions` | 专有字段与比较方式的映射。新增能力字段时必须同步定义。 |
| `historical_quotations` | 用户确认的报价历史。 |
| `historical_quotation_reuse_fields` | 历史缓存可复用字段及分组规则。 |

### 5.3 初始化和重建

目录初始数据来自 `doc/新试验类型及设备能力.xlsx`：

```bash
cd /my_storage/chen/auto-quote
/my_storage/chen/conda/envs/quote/bin/python -m backendV2.core.catalog.bootstrap_database
```

该命令会执行替换目录表的 SQL。运行前必须先备份数据库，并确认确实需要以初始 Excel 覆盖当前测试项目和设备目录。日常新增和修改不使用此命令。

### 5.4 数据库备份与恢复

备份前从实际配置确认主机、端口、用户和数据库名。示例：

```bash
pg_dump --format=custom --file=/my_storage/chen/backups/auto_quote_YYYYMMDD.dump postgres
```

恢复示例：

```bash
pg_restore --clean --if-exists --dbname=postgres /my_storage/chen/backups/auto_quote_YYYYMMDD.dump
```

恢复属于覆盖性操作，应在停写窗口执行，并先确认备份文件可读、目标数据库正确。

## 6. 运行数据维护

一次报价同时使用两个目录：

- `backendV2/agent_workspace/runtime/<run_id>`：输入文件、报价表、校验结果、价格结果、人工快照、导出文件和 Agent 日志；
- `backendV2/core/runtime/<run_id>/state.json`：供列表和状态接口读取的运行状态。

删除或迁移历史运行时，两处目录应按相同 `run_id` 一起处理。运行目录可能包含客户文件、标准资料和模型输出，应按敏感业务数据管理。

建议备份内容：

- PostgreSQL 数据库；
- 两个 runtime 目录；
- `data/cleaned_markdown` 和 `data/origin`；
- 报价单模板；
- Agent 提示词与专用模型配置；
- 数据库初始 Excel 和迁移 SQL。

系统当前没有自动清理运行目录。制定保留周期时，应先确认报价追溯和历史查询要求，再进行归档或删除。

## 7. 标准资料维护

当前报价不执行 OCR、Markdown 清洗或向量索引。Agent 按需直接查阅：

1. `data/cleaned_markdown` 中已准备好的标准文本；
2. 文本不完整、内容混乱或需要读取图表时，查阅 `data/origin` 中的原始 PDF。

维护一份标准时，应保持 Markdown 与 PDF 的标准编号和版本一致。修订号不同的标准必须作为不同资料处理。更新标准资料后，可通过测试报价验证 Agent 是否能按标准号和章节正确定位。

## 8. 版本发布流程

1. 检查工作区，区分本次变更与已有未提交修改。
2. 备份数据库和本次变更涉及的重要运行数据。
3. 更新代码、配置模板或依赖锁文件。
4. 执行后端测试、前端类型检查和前端构建。
5. 若修改数据库结构，先在测试数据库执行迁移并验证目录查询、报价和回收站。
6. 重启受影响服务。
7. 执行健康检查。
8. 使用一个包含多个试验项目的样例文件进行端到端报价，验证结果展示、人工修改、设备切换、全部导出、单个导出和历史报价保存。

验证命令：

```bash
cd /my_storage/chen/auto-quote
/my_storage/chen/conda/envs/quote/bin/python -m unittest discover -s backendV2/tests -p 'test_*.py'

cd /my_storage/chen/auto-quote/frontendV2
npm run lint
npm run build
```

## 9. 故障定位

### 9.1 前端无法访问

依次检查：

```bash
screen -ls
ss -ltnp | rg ':3000'
tail -n 200 /tmp/front-vite.log
curl --max-time 5 http://127.0.0.1:3000/
```

如果日志出现 Vite 读取 `/proc`、`/sys` 等系统路径的错误，通常是开发服务器被异常路径请求触发。重启前端可恢复服务；长期外网部署应使用 `npm run build` 生成静态文件，再由正式 Web 服务提供，而不是直接暴露 Vite 开发服务器。

### 9.2 页面返回 500 或 API 不可用

```bash
ss -ltnp | rg ':7887'
tail -n 200 /tmp/quote-v2.log
curl --verbose --max-time 5 http://127.0.0.1:7887/api/health
```

健康检查失败时，检查 Python 依赖、配置文件、数据库连接和端口占用。健康检查正常但前端失败时，检查 Vite 代理目标。

### 9.3 Agent 运行失败

先查看：

```text
backendV2/agent_workspace/runtime/<run_id>/agent_execution.jsonl
backendV2/core/runtime/<run_id>/state.json
```

重点检查：

- 项目内 Codex CLI 是否存在且可执行；
- `QWEN_API_KEY` 是否有效；
- 专用 profile 是否指向 `qwen3.7-plus`；
- DashScope 网络连接是否正常；
- Agent 是否有权限读取输入、标准资料和运行目录；
- 模型上下文或文件处理命令是否报错。

### 9.4 显示“报价已完成”但结果为空

按顺序检查：

1. `state.json` 是否为 `submitted`；
2. `submit_result.json` 的 `accepted` 是否为 `true`；
3. `quotes/*/quote_table.json` 是否存在；
4. `quotation_results.json` 是否存在且 `items` 非空；
5. Core 日志中结果接口是否报错；
6. 浏览器网络面板中的 `quotation-results` 请求是否成功。

浏览器控制台中扩展脚本的错误不一定来自本系统，应以失败请求的 URL、HTTP 状态和 Core 日志为准。

### 9.5 总价为空

总价计算需要：

- 有效的 `test_project_id`；
- 测试项目存在基本金与单价；
- `pricing_quantity` 不为空且可转换为数字。

设备列表为空不会阻止公式本身计算金额。若总价仍为空，检查当前显示是否来自最新人工快照，以及测试项目或计价数量是否在修改时被设为空。

### 9.6 没有可用设备

检查：

- 测试项目的适配设备集合是否为空；
- 设备是否被软删除；
- 报价的专有字段名是否存在于 `special_field_definitions`；
- 设备和需求双方非空值是否满足比较协议；
- 用户指定的设备是否仍在可用设备列表中。

动态表单字段由适配设备非空能力并集生成。新增设备能力字段时，应同步更新数据库列、设备字段常量、专有字段定义和前端中文映射。

### 9.7 导出失败

全部导出和单个导出都只处理总价非空的项目。检查：

- 当前目标报价是否有总价；
- `doc/quote_tep.docx` 是否存在且格式有效；
- 运行目录是否可写；
- 当前人工快照是否可以正常读取。

成功导出后应同时看到 Word 文件和 `quotation_results_output.json`。后者是最近一次导出快照，多次导出会覆盖旧的导出快照。

## 10. 扩展模块时的同步点

### 新增专有能力字段

需要同步检查：

1. 设备能力数据库列；
2. `DEVICE_CAPABILITY_FIELDS` 与用于动态表单的字段集合；
3. `special_field_definitions` 比较类型；
4. 数据库管理页字段；
5. 前端字段中文映射；
6. 历史报价是否允许复用该字段；
7. 设备匹配与 API 测试。

### 新增 Agent 工具

工具实现放在 `backendV2/core/tools`，命令注册在 `backendV2/core/cli.py`，可执行入口保持为 `quote-core`。工具输出应写入当前 run 目录，提示词只传 run 目录、项目 ID 或标准查询条件，不直接在命令行传输整张报价表。

### 修改报价表固定字段

需要同步检查报价模板、Agent 提示词、结果组装、历史报价表、导出模板映射、前端类型和字段中文映射。固定字段与专有字段继续保持分区，设备能力比较只处理专有字段。

## 11. 安全与审计

- API 密钥和数据库凭据不写入提交的文档、日志或前端代码；
- 运行目录包含客户原始资料，应限制目录权限；
- Agent 以 `danger-full-access` 模式运行，应使用独立服务账户并限制主机网络和文件权限；
- 对目录表、价格、设备能力和历史报价的修改应保留数据库备份；
- 导出快照和人工修改快照可用于定位某次报价采用的数据版本；
- 对外服务建议通过反向代理、TLS 和访问控制提供，不直接暴露开发服务器。
