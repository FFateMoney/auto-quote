# Auto Quote 系统介绍与技术实现

## 1. 文档说明

Auto Quote 是一套面向试验检测场景的自动报价系统。系统接收客户提供的 Word、Excel、PDF、图片或纯文本需求，识别其中的测试项目、试验条件、样品信息和标准号，再结合数据库中的试验类型、设备能力和价格规则完成设备筛选与报价。

系统同时支持：

- **普通报价**：一批上传文件共同描述一份报价需求。
- **批量报价**：一个 Excel 中包含多个独立报价需求，系统先拆分，再逐份执行普通报价流程。
- **标准知识库**：将标准 PDF 经过 OCR、清洗、向量化后用于补充试验要求。
- **人工校正**：当字段缺失、设备无法确定或价格规则不完整时，在前端修改字段并重新报价。
- **历史运行与追溯**：每次运行的状态、日志、模型最终提示词和导出文件都保存在独立运行目录中。

本文档以当前代码实现为准。若本文档与早期设计稿冲突，应优先参考当前代码和本文档。

## 2. 系统整体使用方式

### 2.1 启动系统

系统由一个前端和四个后端服务组成：

| 组件 | 默认地址 | 职责 |
|---|---:|---|
| React 前端 | `http://127.0.0.1:3000` | 上传、查看、编辑和导出报价 |
| 报价服务 | `http://127.0.0.1:8000` | 报价流程编排、运行状态和业务 API |
| OCR 服务 | `http://127.0.0.1:8001` | PDF、图片转 Markdown |
| 清洗服务 | `http://127.0.0.1:8002` | OCR Markdown 清洗 |
| 索引服务 | `http://127.0.0.1:8003` | 标准分块、向量化和检索 |

首次运行前需要安装依赖并准备配置：

```bash
pip install -r backend/requirements.txt
cd frontendV2
npm install
```

复制并修改配置文件：

```bash
cp backend/dev/config.example.yaml backend/dev/config.yaml
```

至少需要配置：

- 登录密码与会话密钥；
- 通义千问兼容 API 的 `api_key`、`model` 和 `base_url`；
- PostgreSQL 连接信息；
- Qdrant 地址及本地 embedding 模型路径；
- Word 解析脚本路径；
- 各服务监听地址与端口。

启动所有后端服务：

```bash
./start_backend.sh
```

启动前端：

```bash
./start_frontend.sh
```

也可以分别启动服务：

```bash
./start_service.sh quote
./start_service.sh ocr
./start_service.sh cleaning
./start_service.sh indexing
```

> `start_backend.sh` 只启动四个后端服务，不会启动前端。前端开发服务器固定通过 `frontendV2/package.json` 在 `3000` 端口启动，并将 `/api` 请求代理到报价服务的 `8000` 端口。

### 2.2 登录

打开前端后，用户使用配置文件中的单一系统密码登录。认证成功后，服务端设置会话 Cookie；除健康检查和认证接口外，报价 API 都受会话认证保护。


### 2.3 普通报价

普通报价适合一个或多个文件共同描述一份需求。

1. 在上传页选择“普通报价”。
2. 上传一个或多个 `.docx`、`.xlsx`、`.pdf`、图片文件，或直接粘贴需求文本。
3. 系统预处理文件并调用模型抽取结构化报价行。
4. 系统匹配标准试验类型、筛选设备并计算价格。
5. 在报价界面查看每个阶段的结果、候选设备、淘汰原因和最终报价。
6. 若状态为“等待人工输入”，修改缺失字段或选定设备后继续报价。
7. 点击导出按钮生成 Word 报价单。

多文件上传时，所有文件会作为同一份报价需求的上下文交给抽取流程。

### 2.4 批量报价

批量报价适合一个 Excel 中包含多个独立报价需求的场景。

1. 在上传页选择“批量报价”。
2. 上传一个 `.xlsx` 文件。
3. 模型通过受控 Excel 读取协议逐步观察表格结构。
4. 模型使用 `create_chunk` 将原 Excel 切分为多个同级的单个报价需求。
5. 每个 chunk 依次进入与普通报价相同的报价流程。
6. 前端使用卡片切换各个子报价。

批量报价遵循以下业务原则：

- 批量模式上传的 Excel 必须被切分为至少两个子报价；
- 所有子报价处于同一层级，不存在 Group 下再嵌套报价的层级；
- Group、样品组、项目组等信息只能作为子报价的共享上下文；
- 每个明确可报价的测试、试验、检验、报告或服务项目，应成为独立子报价。

批量报价卡片区域包含两个逻辑视图：

- **完整视图 A**：保留所有子报价，包括被用户删除的记录，用于审计和恢复。
- **活动视图 B**：只包含未删除的子报价，是前端默认展示和“全部导出”的数据来源。

用户可以删除某个子报价，也可以从回收站恢复。删除是软删除，不会销毁运行记录。

### 2.5 查看阶段结果与人工修改

报价界面保存并展示每个阶段的快照。用户可以切换阶段，观察字段如何从原始抽取逐步变成最终报价。

对当前报价行可以执行：

- 修改试验类型、计价数量、样品数量和重复次数；
- 修改样品尺寸、重量和试验条件；
- 从候选设备中指定最终设备；
- 查看不兼容设备及淘汰原因；
- 提交人工修改并继续报价。

人工修改以 `manual_overrides` 的形式记录，不会只覆盖最终展示值而丢失修改来源。

### 2.6 报价历史

上传页提供报价历史下拉列表。列表项来自 `runtime/runs` 中已有运行的名称。

选择历史运行后，前端直接加载其 `run_state.json`，恢复普通报价或批量报价界面。历史运行能够保留：

- 上传文件信息；
- 各阶段结构化结果；
- 子报价的删除和恢复状态；
- 错误信息与下一步操作；
- 已生成的导出文件。

### 2.7 导出报价单

普通报价只有一个导出范围。批量报价提供：

- **全部导出**：导出所有未删除子报价中已成功报价的行；
- **单个导出**：只导出当前选中的子报价。

导出使用 `doc/quote_tep.docx` 作为模板。系统会根据实际报价行数动态增加表格行，而不是受模板预设行数限制。只有状态为 `quoted` 且存在 `total_price` 的报价行会进入导出文件。

## 3. 系统架构

```text
浏览器 / React 前端
        |
        | HTTP / JSON / multipart
        v
报价服务 backend/quote :8000
  |       |          |          |
  |       |          |          +--> PostgreSQL：试验类型、设备、价格规则
  |       |          +-------------> 通义千问兼容 API：抽取、补充、批量切分
  |       +------------------------> 索引服务 :8003：标准知识检索
  +--------------------------------> OCR 服务 :8001：图片与扫描件识别

标准库离线/管理链路：
原始 PDF -> OCR :8001 -> 清洗 :8002 -> 索引 :8003 -> Qdrant
```

系统采用单仓库、多服务结构。报价服务负责业务编排，其他服务保持独立职责，避免 OCR、文本清洗和向量索引逻辑混入报价核心。

主要目录：

```text
frontendV2/                 React 前端
backend/
  common/                   跨服务配置、认证、日志和公共模型
  quote/                    报价服务与报价领域逻辑
  ocr/                      OCR 服务
  cleaning/                 Markdown 清洗服务
  indexing/                 向量索引与检索服务
  dev/                      开发启动入口
doc/                        设计文档和报价单模板
runtime/runs/               每次报价运行的状态、日志和产物
data/                       标准库处理中间产物
```

## 4. 前端实现

前端位于 `frontendV2`，使用 React 19、TypeScript、Vite、Tailwind CSS、Lucide Icons 和 Motion。

### 4.1 页面职责

前端主要负责：

- 登录和会话状态检查；
- 普通报价、批量报价和文本报价的提交；
- 报价历史选择；
- 运行状态轮询与刷新；
- 阶段快照展示；
- 结构化字段编辑和人工继续报价；
- 子报价卡片切换、软删除和恢复；
- 试验类型别名维护；
- 单个或全部报价导出。

前端不执行文档解析、模型推理、设备筛选和定价。所有业务结果以报价服务返回的 `RunState` 为准。

### 4.2 批量报价前端模型

批量报价的后端数据源始终是完整的 `batch_quotes` 列表。前端展示时过滤 `is_deleted=true` 的项目，因此不会因删除操作丢失历史记录。

当前选中子报价决定：

- 展示哪个子报价的阶段快照；
- 展示哪个子报价的最终表格；
- “单个导出”传递的 `quote_id`。

“全部导出”不传 `quote_id`，后端自动收集所有未删除子报价。

### 4.3 动态表格

结构化报价表以 `FormRow` 为数据源：

- 固定业务字段按列展示；
- 只有实际存在的动态条件字段才展示；
- 模型发现的额外标准要求会形成独立列；
- 可编辑字段提交到 `/api/runs/{run_id}/resume`；
- 候选设备和淘汰设备在独立区域展示。

## 5. 报价服务与 API

报价服务位于 `backend/quote`，使用 FastAPI。它是前端的唯一业务 API 入口，也是整个报价流程的编排者。

### 5.1 主要 API

| 方法与路径 | 作用 |
|---|---|
| `GET /api/health` | 报价服务健康检查 |
| `POST /api/auth/login` | 登录 |
| `POST /api/auth/logout` | 退出登录 |
| `GET /api/auth/session` | 查询会话 |
| `GET /api/catalog/test-types` | 获取标准试验类型 |
| `PUT /api/catalog/test-types/{id}/aliases` | 更新试验类型别名 |
| `GET /api/runs` | 获取报价历史 |
| `POST /api/runs` | 上传文件并创建报价运行 |
| `POST /api/runs/text` | 使用纯文本创建报价运行 |
| `GET /api/runs/{run_id}` | 查询运行状态 |
| `POST /api/runs/{run_id}/resume` | 应用人工修改并继续报价 |
| `PATCH /api/runs/{run_id}/batch-quotes/{quote_id}` | 删除或恢复子报价 |
| `POST /api/runs/{run_id}/export` | 导出全部或单个报价 |
| `GET /api/runs/{run_id}/artifacts/{path}` | 下载运行产物 |

### 5.2 编排器

`QuoteOrchestrator` 是报价主流程的编排入口，负责：

1. 创建运行目录和初始状态；
2. 保存上传文件；
3. 调用文档插件完成预处理；
4. 在批量模式下执行 Excel 协议切分；
5. 对普通需求或每个子报价执行报价阶段；
6. 每阶段保存快照；
7. 汇总运行状态；
8. 响应人工继续报价；
9. 生成 Word 报价单。

编排器只组织流程。具体的文档解析、模型调用、设备筛选、标准检索和定价由独立模块负责。

## 6. 报价阶段

系统定义七个阶段：

| 序号 | 阶段 ID | 中文名称 | 主要作用 |
|---:|---|---|---|
| 1 | `document_extracted` | 文件抽取 | 从文档中抽取第一版结构化报价行 |
| 2 | `test_type_matched` | 实验类型匹配 | 将原始项目名匹配到数据库标准试验类型 |
| 3 | `document_targeted_enriched` | 文档定向补充 | 根据设备能力字段再次定向读取原文 |
| 4 | `equipment_selected_initial` | 设备初筛 | 按样品和试验条件筛选候选设备 |
| 5 | `standard_enriched` | 标准补充 | 从标准知识库补充要求和额外字段 |
| 6 | `equipment_selected_enriched` | 标准补充后复筛 | 使用补充后的条件重新筛选并计算重复次数 |
| 7 | `final_quoted` | 最终报价 | 匹配价格规则并计算总价 |

阶段 3、5、6 可以通过配置开关整体启用或关闭：

```yaml
quote_pipeline:
  document_targeted_enrich_enabled: true
  standard_enrich_enabled: true
  equipment_reselect_after_standard_enabled: true
```

对应环境变量：

```text
QUOTE_DOCUMENT_TARGETED_ENRICH_ENABLED
QUOTE_STANDARD_ENRICH_ENABLED
QUOTE_EQUIPMENT_RESELECT_AFTER_STANDARD_ENABLED
```

当前仓库的 `backend/dev/config.yaml` 将阶段 3、5、6 全部设置为 `false`，因此按当前开发配置运行时，实际主链路为：

```text
文件抽取 -> 实验类型匹配 -> 设备初筛 -> 最终报价
```

被关闭阶段仍会生成带跳过说明的快照。若使用其他配置文件或环境变量启用开关，系统会恢复完整七阶段流程。

关闭阶段时，系统仍保存该阶段的快照和“配置已关闭”说明，使前端阶段序列和历史记录保持稳定。

阶段 6 是整体开关。关闭后不会单独执行其中的重复次数计算；最终报价阶段若发现 `repeat_count` 为空，会自动使用 `1`。

## 7. 核心报价数据模型

### 7.1 `FormRow`

`FormRow` 是贯穿所有报价阶段的核心业务对象。每个对象代表一条可报价项目。

主要字段分组：

| 分组 | 代表字段 |
|---|---|
| 身份与类型 | `row_id`、`quote_id`、`raw_test_type`、`canonical_test_type` |
| 标准信息 | `standard_codes`、`standard_evidences`、`standard_match_notes` |
| 计价信息 | `pricing_mode`、`pricing_quantity`、`sample_count`、`repeat_count` |
| 样品信息 | 长、宽、高、重量 |
| 试验要求 | 温度、湿度、温变速率、频率、加速度、位移、辐照度、水温、水流量等范围 |
| 动态要求 | `planned_standard_fields`、`discovered_standard_fields`、`extra_standard_requirements` |
| 设备结果 | 候选设备、候选设备属性、选中设备、淘汰设备及原因 |
| 报价结果 | 基础费、单价、价格单位、总价和公式 |
| 人工处理 | 缺失字段、阻塞原因、`manual_overrides` |

总价公式为：

```text
总价 = (基础费 + 计价数量 × 单价) × 重复次数
```

### 7.2 `RunState`

`RunState` 表示一次完整报价运行，包含：

- 运行 ID、报价模式、总体状态和当前阶段；
- 上传文件；
- 普通报价的阶段快照与最终行；
- 批量报价的全部子报价；
- 下一步操作、错误和导出产物；
- 创建与更新时间。

### 7.3 `BatchQuoteItem`

每个 `BatchQuoteItem` 是一个独立、同级的子报价，包含自己的：

- `quote_id`、标题和来源摘要；
- 状态、错误、删除状态和删除时间；
- 阶段快照；
- 最终报价行。

系统没有 Group 报价层级。Group 信息只可能存在于子报价来源文本或共享范围中。

## 8. 文档预处理与适配器

### 8.1 插件注册机制

`PluginRegistry` 根据文件后缀选择处理插件：

| 文件类型 | 插件 | 主要处理方式 |
|---|---|---|
| 纯文本 | `TextProcessorPlugin` | 直接形成文本块 |
| Word | `WordProcessorPlugin` | 调用外部 AIWord 脚本导出段落、表格和图片 |
| Excel | `ExcelProcessorPlugin` | 使用 openpyxl 提取行、单元格和嵌入图片 |
| PDF | `PdfProcessorPlugin` | 使用 pypdfium2 将页面渲染为图片 |
| 图片 | `ImageProcessorPlugin` | 保留原图并调用 OCR 服务 |

所有插件最终输出公共的 `NormalizedDocument`。这样，模型调用层不需要分别理解 Word、Excel、PDF 和图片读取细节。

### 8.2 Excel 适配器

普通 Excel 使用 `ExcelAdapter`：

- 使用 `openpyxl` 和 `data_only=True` 读取缓存值；
- 将非空行转换为结构化文本块；
- 将第一条非空行作为可能的表头；
- 使用“表头=值”的方式表达后续行；
- 提取 Excel 内嵌图片并调用 OCR；
- 限制图片数量，避免异常文档占用过多资源。

批量切分后的内存 Workbook 使用独立的 `WorkbookExcelAdapter`。它复用普通 Excel 的行和图片提取逻辑，但额外向模型提供：

- 当前文档是从批量 Excel 切出的独立报价需求；
- `main_range` 是核心区域；
- `shared_ranges` 是共享上下文；
- 保留原坐标造成的空白不代表没有报价内容。

独立适配器避免给普通 `ExcelAdapter` 增加不相关的第二种输入职责。

### 8.3 Word、PDF 和图片

- Word 通过配置的 AIWord 脚本导出段落、标题、表格和图片，再转为统一文档对象。
- PDF 当前主要按页渲染为图片，使视觉模型能够读取版式和扫描内容。
- 图片保留为模型视觉输入，同时调用 OCR 服务得到 Markdown 文本。

## 9. 批量 Excel 读取与切分协议

批量 Excel 不会一次性把整个工作簿文本发送给模型。系统提供受控原子操作，让模型分轮观察并切分，从而降低 token 消耗并保留表格结构。

### 9.1 读取协议

模型可使用：

| 操作 | 作用 |
|---|---|
| `list_sheets` | 获取 sheet 列表 |
| `set_sheet(sheet)` | 切换当前 sheet |
| `get_rows(start, end)` | 读取一段行 |
| `get_columns(start, end)` | 读取一段列 |
| `get_cell(address)` | 读取单元格或其所属合并块 |

读取结果会明确返回合并单元格的完整范围、锚点值、行跨度和列跨度。模型因此不需要根据视觉猜测合并关系。

### 9.2 切分协议

对外只有一个创建操作：

```python
create_chunk(main_range, shared_ranges=None, label=None)
```

- `main_range`：一个独立报价项目自身的矩形区域；
- `shared_ranges`：标题、表头、Group 信息、通用说明等共享上下文；
- `label`：子报价标题。

每个调用产生一个独立的 openpyxl `Workbook`。新 Workbook 保留原单元格坐标，复制所选区域内的值和完整合并块。

### 9.3 协议约束

协议链路包含以下保护：

- 最多进行有限轮数和有限动作数，避免无限循环；
- 读取动作和 `create_chunk`/`finish` 不允许在同一轮混用；
- 模型必须观察范围后才能使用该范围创建 chunk；
- 每个范围必须是合法 A1 notation 且位于 sheet 边界内；
- 任何范围都不得切坏合并单元格；
- 重复 chunk、整表退化和过大的全系列 chunk 会被拒绝；
- 批量模式少于两个成功 chunk 时不能完成；
- 无法可靠切分时必须继续观察，而不是退化为一个总报价。

### 9.4 当前物化边界

当前 `create_chunk` 会复制：

- 指定区域内的单元格值；
- 完整包含的合并单元格；
- 原 sheet 名和原坐标。

当前不会复制：

- 样式、底色、边框、列宽和行高；
- 公式表达式；
- 数据验证、条件格式、图表；
- Excel 嵌入图片。

因此，虽然 `WorkbookExcelAdapter` 具备读取 Workbook 图片的能力，但当前 chunk 物化过程不会把原 Excel 图片带入子 Workbook。这是现有实现边界。

详细协议定义见：

- `doc/Excel 读取协议设计文档`
- `doc/Excel 切分协议设计文档`

## 10. 大模型调用与提示词

### 10.1 调用方式

`QwenRequester` 通过 OpenAI 兼容接口调用通义千问模型。模型、API 地址和密钥来自配置文件或环境变量。

模型主要参与：

- 首次文档结构化抽取；
- 文档定向补充；
- 标准内容字段发现和补值；
- 批量 Excel 协议决策。

调用通常使用低温度以降低随机性，并要求严格 JSON 输出。业务代码会校验返回结构，避免模型输出直接污染运行状态。

### 10.2 分层提示词

提示词模板集中保存在 `backend/quote/llm/prompts.json`，运行时再注入：

- 标准试验类型列表；
- 文档文本块、表格内容和视觉资产；
- 设备能力支持的目标字段；
- 标准检索证据；
- 批量 Excel 工具观察结果；
- 批量 chunk 的提取提示。

首次抽取的主要目标是从标准试验类型列表中选择 `canonical_test_type`，并抽取通用字段。后续阶段再根据设备能力和标准证据补充针对性字段，避免首轮提示词固定绑定某一种试验。

### 10.3 Prompt 日志

每次实际发送给模型的最终提示词会写入：

```text
runtime/runs/<run_id>/model_prompts/<时间戳>_<请求名称>.txt
```

批量 Excel 每轮协议交互另外写入：

```text
runtime/runs/<run_id>/batch_excel_protocol_turn_<序号>.txt
```

这些日志用于分析：

- 模型实际看到了哪些内容；
- 是否包含无关或重复信息；
- 字段解释是否清晰；
- 批量切分在哪一轮做出了错误判断；
- token 过大的来源。

为避免日志文件异常膨胀，视觉输入通常记录元数据而不是完整图片字节。

## 11. 试验类型、设备筛选与定价

### 11.1 PostgreSQL 目录

报价服务通过 `CatalogGateway` 从 PostgreSQL 加载核心目录：

| 数据 | 用途 |
|---|---|
| `test_types` | 标准试验类型、别名、基础费和计价方式 |
| `equipment` | 设备尺寸、负载、温湿度、频率等能力属性 |
| `test_type_equipment` | 试验类型和可用设备关系 |
| `equipment_pricing` | 按试验类型、设备和数量区间定义的价格规则 |

试验类型别名可以在前端维护，用于改善名称匹配。

### 11.2 试验类型匹配

首轮模型已从标准列表中选择标准试验类型，随后内核结合数据库名称和别名完成标准化匹配，并写入 `matched_test_type_id`。

未匹配到标准类型时，设备和价格规则无法可靠确定，报价行会进入等待人工输入状态。

### 11.3 设备筛选

设备筛选根据试验类型关联设备，再逐项检查：

- 样品长、宽、高、重量是否超出设备能力；
- 温度、湿度、频率、加速度、位移等要求是否兼容；
- 设备是否缺少判断所需的能力字段；
- 设备状态和能力属性是否允许执行该试验。

筛选结果同时保留：

- 兼容设备 ID 和能力概览；
- 被淘汰设备；
- 每台被淘汰设备的具体原因与缺失字段。

这使前端不仅展示“选了哪台设备”，还能够解释其他设备为什么不可用。

### 11.4 重复次数

阶段 6 启用时，系统会根据样品数量、样品尺寸和设备容量计算建议重复次数，并优先保留人工设置。

阶段 6 关闭时，不进行该计算。最终定价发现 `repeat_count=None` 时统一按 `1` 处理。

### 11.5 定价

系统根据标准试验类型、选中设备和计价数量匹配价格规则。成功匹配后计算：

```text
total_price = (base_fee + pricing_quantity * unit_price) * repeat_count
```

下列情况会阻塞最终报价：

- 没有选中设备；
- 缺少计价数量；
- 没有匹配到适用价格规则；
- 必要业务字段仍缺失。

## 12. 标准知识库

标准知识库是一条独立于报价上传的处理链路：

```text
原始标准 PDF
  -> OCR 服务
  -> Markdown 清洗服务
  -> 索引服务分块和向量化
  -> Qdrant
  -> 报价流程按需检索
```

### 12.1 OCR 服务

OCR 服务位于 `backend/ocr`，使用 PaddleOCR PP-StructureV3，将 PDF 或图片转换为 Markdown。

主要能力：

- 页面布局与区域识别；
- 表格识别；
- 可配置的文档方向、去畸变、公式、印章和图表识别；
- 标准库目录的增量同步与全量重建；
- 单文件 OCR HTTP 接口。

主要接口：

| 接口 | 作用 |
|---|---|
| `POST /api/ocr/markdown` | 单文件转 Markdown |
| `GET /api/ocr/library/status` | 查询标准库 OCR 状态 |
| `POST /api/ocr/library/sync` | 增量 OCR |
| `POST /api/ocr/library/rebuild` | 全量重建 OCR 结果 |

### 12.2 清洗服务

清洗服务位于 `backend/cleaning`，负责将 OCR 结果整理为适合检索的 Markdown：

- 使用 BeautifulSoup 和规则处理混杂 HTML；
- 将 HTML 表格转换为 Markdown；
- 展开 `rowspan` 和 `colspan`；
- 移除无意义标签和 CID 字符；
- 修复断词和异常空白；
- 保留对标准检索有价值的结构。

主要接口：

| 接口 | 作用 |
|---|---|
| `POST /clean` | 清洗一段 Markdown |
| `GET /health` | 健康检查 |

### 12.3 索引服务

索引服务位于 `backend/indexing`：

- 按 Markdown 标题和大小限制分块；
- 使用本地 Qwen3 Embedding 模型生成向量；
- 使用 Qdrant 余弦距离保存和检索；
- 为标准 ID、来源等字段建立 payload 索引；
- 支持本地 reranker 模型配置。

默认集合名为 `standard_kb`，默认向量维度为 `4096`。

主要接口：

| 接口 | 作用 |
|---|---|
| `POST /search` | 按查询文本和可选标准号检索 |
| `GET /health` | 健康检查 |

### 12.4 报价阶段中的标准补充

标准补充启用时，报价服务根据试验类型、标准号和目标字段构造检索查询。`StandardRetriever` 调用索引服务获取标准片段，解析器过滤无效内容并形成证据。

模型随后完成两类工作：

1. 识别标准中实际存在且系统支持的设备能力字段；
2. 提取设备能力字段之外的额外标准要求，并保留名称、内容和来源章节。

检索服务失败时，报价服务会容错返回空结果，而不是使整个报价服务崩溃；对应报价行可能转为等待人工输入。

## 13. 运行状态、日志与可追溯性

每次报价运行对应一个目录：

```text
runtime/runs/<run_id>/
```

典型内容：

```text
run_state.json                         当前完整运行状态
run.log                                业务阶段日志
uploaded/                              原始上传文件
model_prompts/                         实际发送给模型的最终提示词
batch_excel_protocol_turn_*.txt        批量 Excel 协议轮次记录
excel_images/                          Excel 图片预处理产物
报价单_<run_id>.docx                   全部报价导出
报价单_<run_id>_<quote_id>.docx        单个子报价导出
```

`RunStore` 负责将 Pydantic 状态模型写入 `run_state.json`。每个阶段完成后立即保存快照，因此：

- 页面刷新后可以恢复；
- 历史查询不需要重新调用模型；
- 可比较各阶段字段变化；
- 批量报价中某个子报价失败不会丢失其他子报价结果；
- 可以通过日志定位提示词、切分、设备筛选或定价问题。

运行目录包含客户需求和模型提示词，可能涉及敏感信息，应按部署环境设置访问权限、备份和清理策略。

## 15. 技术边界与维护注意事项

### 15.1 当前边界

- 报价运行是同步长请求模式，大文件和批量报价耗时会直接反映在请求时长上。
- 批量 Excel 必须能通过矩形范围表达子报价；复杂的非矩形语义布局可能需要更多协议能力。
- chunk 当前不复制 Excel 图片、样式和图表。
- PDF 主要以页面图片交给视觉模型，文档页数和图片数量会影响 token 与耗时。
- 标准知识库补充是否执行取决于阶段开关和索引服务可用性。
- 最终导出只包含已经成功报价的行，不包含等待人工输入或失败行。

### 15.2 维护原则

- 新文档类型应通过新增插件接入，不应把格式判断散落到编排器。
- 新的内存输入形态应使用独立适配器，避免让现有适配器承担混杂职责。
- 新报价阶段应定义明确输入、输出和快照，不应在其他阶段中隐式执行。
- 批量报价必须保持“批量文档 -> 同级单个报价”的唯一业务模型。
- 模型输出必须经过结构化校验，不能直接作为可信业务状态。
- 人工修改必须留下 override 记录。
- 与客户数据相关的 prompt、上传文件和运行状态必须视为敏感数据。

## 17. 一次批量报价的完整数据流示例

```text
用户选择批量报价并上传 Excel
  -> 报价服务创建 runtime/runs/<run_id>
  -> 保存原文件和初始 RunState
  -> QwenRequester 启动批量 Excel 协议循环
  -> 模型调用 get_rows/get_columns/get_cell 观察结构
  -> 模型为每个独立项目调用 create_chunk
  -> ChunkProtocol 校验范围、边界和合并单元格
  -> 每个 chunk 物化为独立 Workbook
  -> WorkbookExcelAdapter 转换为 NormalizedDocument
  -> 对每个子报价执行七阶段报价流程
  -> 每阶段写入 BatchQuoteItem 快照和 run_state.json
  -> 前端用卡片展示未删除子报价
  -> 用户补录缺失字段或删除无效子报价
  -> 用户选择全部导出或单个导出
  -> 报价服务动态生成 Word 报价单
```

该流程的核心约束是：批量切分只负责把一个大文档变成多个独立需求；切分后的每个需求继续复用同一套普通报价流程，而不维护另一套报价逻辑。
